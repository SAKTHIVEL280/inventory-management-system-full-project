- **DB-207** (Multi-tenant M1 — per-tenant document numbers): `migrations/0013_multitenant_m1_per_tenant_doc_numbers.sql` (idempotent, single transaction) + `…_rollback.sql`. Converts the **global** single-column `UNIQUE` on every document-number column into a **composite** `UNIQUE(company_id, <number>)` so numbers are unique within a tenant but may repeat across tenants — without it, two tenants generating e.g. `INV-00001` would collide. Tables/columns: `purchase_orders.po_number`, `goods_receipt_notes.grn_number`, `purchase_returns.return_number`, `quotations.quotation_number`, `proforma_invoices.proforma_number`, `sales_orders.so_number`, `sales_invoices.invoice_number`, `sales_returns.return_number`, `return_delivery_notes.rdn_number`, `rdn_credit_notes.credit_note_number`, `payments.payment_number`, `inventory_counts.count_number`. Implemented as a **dynamic** `DO` block that, per table: skips it if `company_id` is absent; finds and drops the existing single-column UNIQUE *constraint* by shape (not hard-coded name — handles PG's auto-generated `<tbl>_<col>_key`); drops any standalone single-column UNIQUE *index*; then creates `ux_<tbl>_company_number` on `(company_id, <number>)`. No behaviour change for the existing single tenant (`UNIQUE(company_id, number)` ≡ `UNIQUE(number)` when one company_id exists; all current numbers satisfy it). **`01_schema.sql` is intentionally unchanged** for M1: the base schema does not declare `company_id` on these business tables (that is applied by `run_migration.py` after the base schema), so the conversion lives in `run_migration.py` — mirrored there as the same `DO` block, which runs *after* the existing company_id sync block guarantees the column exists. **Not executed against the user's database** (run on deploy; backup first).
