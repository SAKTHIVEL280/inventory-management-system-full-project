### BRD Bugfix v1.5 (docs/requirements/BRD_Bugfix_v1.5.md)

- **BE-205** (MCN-BUG-004-ii): New `PUT /api/v1/grn/{id}/confirmed-details` (`grn_write`) — edits Batch/Qty/Rate/Expiry/MFG/Remarks of a **confirmed** GRN. Reconciles stock by reversing the original ledger postings and re-posting corrected values (same mechanics as confirm/reverse), recalculates GRN totals (payables derive from these), and writes a field-level audit entry (field, old, new, user, timestamp). Guards: blocks edit when a non-cancelled payment is allocated or a confirmed purchase return exists, and when a reduction would drive on-hand stock negative. Adjusts PO `received_quantity` by the per-line delta and recomputes PO status. Draft GRN editing (`PUT /api/v1/grn/{id}`) is unchanged. New schemas `GRNConfirmedEditRequest`/`GRNConfirmedEditItem`. GRN number/supplier/created details never modified.
- **BE-206** (MCN-BUG-005): `GET /reports/sales` now joins `customers` (via `bill_to_customer_id` → `customer_id` fallback) and returns `customer_name` per invoice row.
- **BE-207** (MCN-BUG-006): Sales Invoice ("Sales Order" — the retired SO module redirects to invoices) edit versioning. `audit_logs.version` populated on each successful full-resource invoice edit (`PUT /api/vN/invoices/{id}`) via `log_audit_event`; first edit = 1, incrementing; creation/non-edit/status changes stay NULL; append-only rows make it immutable. `int_to_roman()` helper added. `/reports/action-logs` returns `version` + `version_label` ("Version I", ...).
- **BE-208** (Action Logs 500 fix): `_ensure_audit_logs_table` now self-heals `audit_logs.company_id` (+ index) and `audit_logs.version`. Root cause: the action-logs SELECT and the `log_audit_event` INSERT reference `company_id`, which was missing on deployments predating the multi-tenant migration → `UndefinedColumn` → 500. Idempotent; runs on every audit access.
- **BE-209** (Human-readable audit descriptions): New centralized `compose_audit_service.compose_audit_description()` builds plain-business-language audit text — document number instead of UUID, past-tense business verb (created/updated/confirmed/issued/reversed/cancelled/...), and field-level "`<Field>` changed from `<old>` to `<new>`." lines from a `details.changes` list. Money fields (rate/amount/...) format as INR (paise→rupees); verb detection is path-segment-aware so `/grn/{id}/confirmed-details` reads as *updated*, not *confirmed*. `_build_human_readable_description` (write-time) now delegates to it. `/reports/action-logs` **re-composes** each row's description at read time using the resolved document number (`_extract_document_reference`) — so existing rows whose stored text held a UUID are upgraded too — and only falls back to an `Amount:` line when no field changes were captured (replaces the old `| Amount:` suffix). Applies across all financial modules (Sales, Purchase, Inventory, Accounts/Payments, Returns, RDN). Versioning (Version I/II/...) unchanged. A reusable `build_audit_changes()` helper (JSON-safe coercion via `_json_safe`, drops no-op changes) lets endpoints capture exact field-level old→new values. `update_invoice` (PUT, sales.py) snapshots pre-edit values and records header changes (Amount/Customer/Invoice Date/Due Date/Invoice Type/Remarks/Discount) **plus per-line-item** changes (Quantity/Free Quantity/Rate/Discount %/Batch and line item added/removed); `update_purchase_order` (PUT, purchase.py) records Supplier/Order Date/Expected Delivery/Remarks/Discount/Amount changes; `update_payment_status` (PATCH, payments.py) records the Status change (e.g. *Status changed from Pending to Cleared*, title-cased). The `AuditTrailMiddleware` merges any endpoint-provided `request.state.audit_changes`/`audit_reference` into the single baseline audit row (no duplicate rows); the payment endpoint passes `changes` through its existing explicit `log_audit_event` call.

### BRD Bugfix — GRN Batch / Invoice Edit-After-Issue / Country Master

- **BE-210** (GRN — Batch mandatory): Batch number is now required on every GRN line. Enforced server-side (HTTP 400, per-line message "Line item N: Batch number is required.") in `create_grn` (`POST /api/v1/grn`) and `update_grn` (`PUT /api/v1/grn/{id}`) inside the line loop, and in `update_confirmed_grn` (`PUT /api/v1/grn/{id}/confirmed-details`) pass-1 validation ("Batch number is required for every line item."). Validation lives at the router level (not on the shared `PurchaseLineItemRequest`, which is also used by Purchase Orders where batch is not captured) so PO creation is unaffected. No schema change — `grn_items.batch_no` already exists.
- **BE-211** (Sales Invoice — Edit after issue): New `PUT /api/v1/invoices/{id}/issued-details` (admin-only via `require_role("admin")`) edits an already-issued invoice. Mechanics mirror the GRN confirmed-edit: reverses the invoice's original stock `sale` postings (`adjustment`/`inv_edit_reversal`, +qty/+free), validates stock availability per product against the restored on-hand, rebuilds line items, recomputes tax/totals (`calc_line_item` + `round_paise_to_nearest_5`), re-posts corrected `sale` ledger entries, refreshes the materialized view, and recomputes `amount_due` and payment `status` (so the derived receivable stays correct). Field-level changes (header Amount/Customer/Dates/Type/Remarks/Discount **plus** per-line Quantity/Free/Rate/Discount %/Batch and line added/removed) are captured via `build_audit_changes` and merged by the audit middleware into one readable audit row with acting user + timestamp. Guards (financial integrity): blocks edit when a non-cancelled payment is allocated to the invoice or a confirmed sales return exists, and when the corrected quantity would exceed available stock. Status must be in `{issued, partial_paid, paid}`; draft invoices continue to use `PUT /api/v1/invoices/{id}` (unchanged).
- **BE-212** (Customer & Supplier — Country master): New `app/utils/countries.py` `COUNTRY_MASTER` (complete country list, 198 entries). The Customer (`GET /api/v1/customers/customization-options`) and Supplier (`GET /api/v1/suppliers/customization-options`) endpoints now **union** the master list with any company-specific custom country values from `customization_options` (deduped case-insensitively, sorted) instead of falling back to a 6-item default only when empty — so the country typeahead always offers the full list while still honouring custom entries. Existing records are unaffected (free-text country values still round-trip). No schema change.
- **BE-213** (Clear validation error messages): Added a global `RequestValidationError` handler in `main.py`. Previously FastAPI returned request-body validation errors (422) as a raw list of terse, field-less messages (e.g. "Input should be a valid integer"), which reached the UI as a generic "Invalid input. Please check the entered values." The handler now returns a single readable sentence that **names the offending field and states the problem**, e.g. "Items #1 → Quantity: must be a valid number", "Receipt date: Field required", "Supplier id: must be a valid UUID" (`_humanize_validation_location` renders the pydantic `loc` path; common pydantic phrasings are rewritten — "Input should be" → "must be", "Value error, " stripped). Applies to every endpoint, so users see exactly which field/line is wrong. GRN batch/date/tolerance rules already return clear string messages (BE-210) and are unchanged. Also made `_enforce_supplier_gstin_for_gst_purchase` (GRN) messages **actionable** — when a Non-Registered GST supplier is missing State/State Code, the error now names the supplier and tells the user to edit the supplier to add it (e.g. "Supplier 'abcdss' has no State set. Edit the supplier and add its State before creating a GST GRN."). These are raised as a `detail` list of strings, which the frontend now renders correctly (see FE-213).
